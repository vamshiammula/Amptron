# Amptron performance review — 7 September 2026

Scope: source inspection of routing, content loading, media components, admin/dealer loading, authentication, FAQ matching and static serving; sizes measured from the latest existing dist output. The findings below record the initial review; the implementation status follows. This is not a production Lighthouse, load-test or field-latency benchmark. Local file reads and preview restarts were unstable during review.

## Prioritized findings

1. **Verify production build configuration first.** The existing index source map lists scheduler.development.js, react-dom.development.js and react-dom-client.development.js; dist also includes jsx-dev-runtime. The cause is not established. Inspect build-time NODE_ENV and Vite mode, rebuild in production and assert development runtime is absent. Do not infer production speed from the current dev server.
2. **Media source clarified: Supabase.** The user confirmed media is hosted in Supabase. Missing former local files are intentional, not an integrity failure. Validate referenced hosted objects; do not restore stale dist files as the source of truth.
3. **Optimize media delivery.** Existing built NIRA GLB is approximately 67 MiB, film approximately 11 MiB, and nine PNGs approximately 1.4–1.7 MiB each. Create visually verified web derivatives: responsive WebP/AVIF stills, genuinely small thumbnails, mobile/desktop video encodes and a compressed GLB with optimized textures. Keep master files. No percentage reduction is guaranteed until tested.
4. **Load 3D on explicit intent.** ScooterStage defaults to 3D and imports the viewer immediately on Explore. Prefer a fast poster with a View in 3D control; load the GLB and renderer only then. Keep the gallery and film accessible while it loads. Homepage separation already helps.
5. **Split public route code.** App.tsx eagerly imports all public pages including calculator and model detail. Admin, portal and chat are split already. Split non-home routes and route-specific CSS; prefetch likely destinations on user intent. Avoid fragmenting every tiny component.
6. **Improve homepage video scheduling.** HeroFilm calls play on mount except for reduced motion. This starts media fetching despite preload=metadata. Prioritize a lightweight poster, avoid automatic playback on data-saving connections, pause when offscreen/hidden and preserve user pause intent. Keep native controls and reduced-motion behavior. Inspect actual video dimensions before changing aspect ratio or cropping.
7. **Admin and dealer request fan-out.** Admin loads profile then ten endpoints; dealer loads profile then four. Initial loading waits for the group, and mutations frequently reload everything. Load overview first, each tab on demand, cache within the signed-in session and invalidate affected data only. Preserve tenant isolation and error recovery.
8. **Real server pagination and aggregate counts.** Admin list endpoints for orders/tickets and FAQ support queries lack explicit pagination; UI slicing does not reduce database or network work. Add bounded pagination/filter contracts and matching indexes based on query plans. Overview currently fetches up to 500 applications to calculate counts, causing both unnecessary transfer and a capped total. Calculate aggregates in the database.
9. **Authentication round trips.** Each protected endpoint performs getUser plus an account lookup before business queries. Request fan-out multiplies this. Reduce redundant endpoint calls first; consider a combined overview endpoint. Never remove authentication/RLS or cache authorization without defined expiry and revocation behavior.
10. **Public content fetching.** Global provider fetches full published model rows and blog metadata together on every fresh mount. Separate blog fetching by route, select necessary columns, deduplicate in-flight reads and cache only public data with deliberate invalidation. Preserve published/empty-catalog semantics.
11. **Chat loading and matching.** Lazy ChatWidget is rendered immediately, so its chunk is requested immediately; suggestions fetch before a conversation opens. Defer full chat UI and suggestions until intent/idle. FAQ service already has LRU and FAQ-list caches plus lexical matching. However DB-cache lookup precedes the lexical tier on every LRU miss, lexical successes are not placed in LRU, and embedding responses await a cache write. Measure these stages; consider versioned lexical-result caching and shared in-flight loads. Preserve answer freshness and use a reliable background mechanism if moving writes off the response path.
12. **Static caching.** Express fingerprints /assets with a one-year immutable policy but gives /products no-cache. That allows storage/revalidation; it does not mean no storage. Version product filenames before assigning long-lived immutable caching. Verify actual CDN headers separately for Vercel and Express deployments; Express middleware does not govern Vercel static delivery.
13. **Measurement and regression budgets.** Capture production mobile/desktop cold and warm runs on home, models, NIRA, calculator, admin and dealer. Measure LCP/INP/CLS, transfer size, JS execution, media startup, failed requests and API p50/p95. Add server timing around auth, database and embedding stages without logging personal queries. Use staging/memory fixtures for load tests, not production submissions.

## Preserve existing strengths

Keep the approved design, local fonts, aspect-ratio image containers, lazy below-fold MediaFrame images, dynamic model-viewer import, portal route splitting, Express compression, hashed-asset caching, FAQ caches and parallel independent reads. Do not lazy-load the main hero poster. Calculator optimization should follow interaction profiling; no evidence currently justifies workers or a rewrite.

## Acceptance and order

First verify asset integrity and production mode; then optimize media and defer 3D; next split public routes and defer chat; then implement tab-driven portal loading and database pagination/aggregates; finally tune measured API/FAQ stages and deployment geography. Preserve existing contracts and tests when changing pagination or catalog behavior.

Web targets: LCP <=2.5 seconds, INP <=200 ms and CLS <=0.1 at the 75th percentile. These are targets, not measured results. Establish API targets from production-region baseline and endpoint workload; do not promise zero latency.

References: https://web.dev/articles/vitals and https://web.dev/learn/performance/video-performance

## Implemented optimization pass

- Production build sets NODE_ENV before loading Vite and rejects development React runtimes. Source maps are disabled. Public routes and workspace CSS load separately.
- Nine approved Supabase PNG originals (15,254,745 bytes total) now have content-hashed WebP derivatives (706,646 bytes total) and dedicated thumbnails (32,484 bytes total). Originals remain untouched. All uploaded object URLs returned HTTP 200; a derivative GET returned `public, max-age=31536000`. HEAD initially returned different cache headers, so verify GET when auditing delivery.
- Catalog mapping upgrades known original NIRA photo URLs to the derivative URLs, including remotely supplied catalog content.
- Explore opens with photos; the 3D renderer and model load only after choosing 3D. Homepage video respects data saving and pauses offscreen or in hidden tabs.
- Chat loads after a short delay or explicit intent, and suggestions wait until opening. Concurrent public-content requests share one in-flight read. Successful lexical FAQ answers enter the existing LRU.
- Admin and dealer sections request relevant data instead of every section on each refresh. Dealer overview still needs its summary collections. Admin overview, orders and tickets additionally load account names for labels and search; unopened sections show no count until successfully loaded. Catalog drafts remain mounted after first visiting the section.
- Admin application totals use count-only database queries instead of downloading capped application lists. Read-only queries were verified against Supabase.
- Retired Storm media checks now validate historical audit metadata rather than requiring obsolete local binary copies.

Measured main JS is approximately 271 KB versus 908 KB in the original artifact. The complete initial JS preload set is 634,534 raw bytes / 186,753 locally gzip-compressed bytes. These are build sizes, not measured user latency; the original full preload total was not captured.

Remaining work requiring separate measurement includes video/GLB compression, paginated list contracts, query-plan-based indexes and production mobile/desktop latency baselines. The large 3D bundle remains available on demand. No authentication or RLS rules were weakened, and no original media was deleted.

### Final verification after recovery

On 7 September 2026, `npm run verify` passed formatting, lint (no warnings), type checking and all 251 application tests. All 36 browser tests passed across Chromium desktop and mobile WebKit using the memory repository. The current production build passed the development-runtime guard and server compilation. Main JavaScript is 271,396 bytes; the complete initial JavaScript preload set is 634,534 raw / 186,753 locally gzipped bytes.

The development server starts from `~/Developer/Amptron`, with Vite ready in 144 ms in the observed local run. A controlled source-file timestamp change triggered a graceful API restart without the earlier forced kill. One listener remains on each development port (5173 and 3001); duplicate startup is rejected clearly. Fresh interactive zsh finds `compdef` without an error. These are local observations, not production latency percentiles.

Live browser checks confirmed the homepage film plays, labels remain readable, and the NIRA gallery navigates all nine photos. The existing signed-in admin session successfully loaded overview and orders, including account names and accurate count badges. Dealer workflows and mutations were tested with mocks/memory fixtures; live dealer-role and mutation paths were not exercised.

### Follow-up: local verification stalls

macOS process sampling showed all four test-runner filesystem workers blocked in read calls. The open source files had the `dataless` flag (cloud-only placeholders), confirming local source availability as a blocker. Requested local downloads of 183 source files through Foundation's ubiquitous-item API; no cloud media, originals, or application data were deleted. The retired-media audit check passed both tests in isolation. The gallery mapping was simplified to pair manifest images and thumbnails directly, without reverse URL lookup.
